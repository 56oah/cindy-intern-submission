# PR 看板设计

## 界面形态

我认为是常驻面板。这个需求的重点是用户随时能看见待处理 PR，并能直接点击交给 Agent，面板最适合作为固定入口。纯工具需要先在聊天中发起调用。聊天卡片适合展示一次结果，容易被后续消息淹没。最小版只在打开和手动刷新时获取数据，代价是状态不会自动更新，但实现简单，也避免不必要的后台请求。

## 联网方式

由插件主动联网，因为用户打开面板时就应该看到 PR，不应先等 AI 调用工具。Cindy 对这种自主请求要求提前声明域名，因此插件在 network.hosts 中列出 api.github.com，并通过 cindy.fetch 访问。另一种情况是 Agent 正在调用插件工具，普通 HTTPS 请求可携带该次调用的真实 callId，不必预列域名。但只要使用宿主托管令牌，仍须声明凭证。两者的权限条件不能混用。

## Token 管理

最小版由用户在插件设置页提供 GitHub Token，交给 Cindy 的保险库保存，再由宿主向 api.github.com 注入认证信息。插件不把令牌写进代码、普通配置、聊天或日志。这样不用另搭授权服务，但用户需要自己创建和管理令牌，这是当前小版本可以接受的操作成本。

权限要按实际接口选择。fine-grained PAT 可以限制仓库和部分读取权限，但不能据此保证能读取私有仓库的 Checks，完整读取可能需要用户选择已有 OAuth 凭证或带 repo scope 的 classic PAT，而 repo scope 包含写权限，不能称为只读。插件自身只发读取请求，缺权限就显示未知并说明原因。

## 交给 Agent

点击 PR 后，先由插件收集当前提交的检查结果、失败输出、可获取的注解和作业链接，再用 cindy.tasks.create/send 创建可见任务，把这些资料交给 Agent。用户因此能查看过程，也能继续补充信息，不用只盯着一个按钮等结果。独立看板更适合新建任务，而不是套用聊天卡片关联原任务的 agent.run。

交接时要把“请求已受理”和“分析已完成”分开。资料不够就让 Agent 说明缺少什么，不能只传一个链接便声称查明原因。PR 描述和日志也只是待分析数据，不能成为推送代码或重跑 CI 的授权。

接口依据：Cindy v0.1.121 的插件作者手册 `plugin-panels.md`, `plugin-network.md`, `plugin-agent-tasks.md`。
