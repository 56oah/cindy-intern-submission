# 工程判断

## A1 日期问题

### (a) 方案判断

我赞成由程序提供日期，但不赞成只因为改动小就直接上线。这个方案的好处在于模型每次都能看到时间，用户不用反复提醒。但用户问“今天／这周”，通常只需要当地日期、星期和时区，精确到秒没有必要。服务器时间若没有标明时区，也可能给出错的日期。

另一个问题是提示词缓存。缓存依赖相同的前缀，靠前的时间每秒变化，可能让后面的固定内容和长对话历史无法继续复用，增加费用和等待时间。影响取决于插入位置和模型接口，不能说修改 system prompt 就一定清空所有缓存。给出日期也不等于知道本周的事情，实时事实仍需查询。

### (b) 上线影响

如果这行时间加在公共请求入口，所有经过该入口的请求都会受影响，包括根本不问日期的用户。日期相关回答可能改善，但原本缓存命中较多的长会话和多步 Agent 可能变贵、变慢。没有缓存的短请求通常只是多发送这一行。没有实际调用数据，不能给出一个统一的影响比例。

这类退化通常不会报错，只看功能是否正常很容易漏掉。我会按模型和会话长度比较改动前后的缓存使用量、单轮费用和首字延迟，再单独检查日期回答是否变准。海外用户和午夜附近的请求会重点看，否则可能付出了缓存代价，却仍然没有解决日期错误。

### (c) 我的方案

我的方案是保留固定 system prompt 和已有历史，在每个新用户轮次的末尾，由宿主补充一段日期上下文，例如“本轮日期为 2026-11-03，星期二，Asia/Shanghai时区。今天和这周以此为准”。优先采用用户设置的时区，没有时使用设备时区。新轮次重新取日期，旧消息保留原来的时间参照，同一轮普通工具调用不必反复刷新秒数；需要精确时刻或长任务跨天时，再调用时间工具。

这样模型不必等用户提醒，又能尽量保留前面的稳定内容。上线前要实际追问“今天几号”“这周从哪天到哪天”，覆盖跨午夜、周界、年界和不同时区，并与原方案比较缓存、费用和延迟。验收目标是回答使用了正确日期，而不只是请求里出现了日期。

## A2 配置排查报告

我不会直接采信 AI 的结论，也不会立即安排一周的重写。报告虽然找到了配置未更新的直接原因，但还没有证明客户端的设计存在缺陷。

这份报告存在三个主要问题：

（1）没有区分直接原因和真正的根因。 远端和本地缓存的 updatedAt 相同，因此客户端继续使用旧配置，这个判断虽然没问题，但需要先确认配置的更新规则。如果服务端每次修改配置都必须更新 updatedAt，那么问题可能是发布时漏改了时间，而不是客户端代码有缺陷。

（2）影响范围判断过大。 报告认为所有用户都会受到影响，但目前只能确认持有旧缓存、且执行到这段判断逻辑的客户端会受影响。首次加载配置的用户不一定存在这个问题。

（3）修复方案缺少依据。 直接删除时间比较，可能导致旧配置覆盖新配置，改成逐字段深比较，虽然能发现配置内容不同，但无法判断哪份配置更新。另外，报告也没有提供需要一周重写的充分依据。

我会先进行最小范围的验证。首先，查看配置发布规则，确认 updatedAt 是否必须随配置内容更新。接着在测试环境中保留原来的客户端代码和旧缓存，只把远端配置的 updatedAt 改成更大的值，重新执行配置加载流程。重点检查两个问题：

（1）客户端是否成功获取并使用包含 46 个模型的新配置，新模型和价格能否正确显示。

（2）如果仍然没有生效，进一步检查问题出在配置拉取、缓存更新，还是界面展示。

通过这个实验，可以判断问题是否由版本未更新引起，而不用一开始就重写整个模块。然后我会根据验证结果确认修复方案。

如果确认是发布时漏改了 updatedAt，就优先按照正常流程重新发布配置，并增加发布检查，避免以后出现配置内容修改了、版本却没有更新的情况。如果确认客户端确实没有按照约定处理配置，再针对具体问题修改代码，而不是直接重写整个模块。修改后我还会回归测试正常版本更新、旧版本处理以及拉取失败时保留缓存等场景。
