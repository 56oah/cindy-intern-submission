# 收工

按以下顺序执行。只报告实际执行和看到的结果；不自动提交、推送或发布。遵守当前仓库的 AGENTS.md 和已有测试约定。

## 准备范围

确认仓库根目录、当前分支和本次任务的改动基准。优先使用用户指定的基准，或本次开发开始时已经记录的提交；核实它存在且属于当前历史。若没有可靠基准，依据对话和 `git log --oneline` 查找，不把 HEAD、最近一次提交或当前分支的上游自动当作任务起点。仍无法确认时，继续检查可确认的提交和全部工作区改动，在结果中写清已检查范围与缺失基准，不能声称已覆盖本次全部提交。

读取 `git status --short`、`git diff --stat`、`git diff --cached --stat`、`git ls-files --others --exclude-standard`。保留用户原有的暂存状态和改动；不要通过 reset、checkout 或 stash 清空工作区。

## 1. 运行测试

先读项目开发说明、包脚本、锁文件和 CI 中的测试入口，使用项目已有命令与包管理器运行约定测试。没有统一入口时，按受影响模块选择现有测试，并写明覆盖范围；不能拿语法检查或构建成功代替测试通过。若仓库确实没有测试，明确写“无现有测试”，运行适用的构建或静态检查并说明限制，不为凑结果新增无意义测试。

记录命令、退出码和失败摘要。遇到依赖、权限或外部服务问题，先定位原因；能在本次授权范围内修复的直接修复，无法修复的记录阻碍。测试失败或无法运行时仍继续第 2、3 步，不能将本次收工标为全部通过。

## 2. 检查全部本次改动

有可靠基准时，查看 `git log --oneline BASE..HEAD` 和 `git diff BASE HEAD`，其中 BASE 替换为已核实的提交；再分别查看 `git diff --cached` 与 `git diff`，覆盖本次已提交、已暂存和未暂存内容。即使工作区干净，也必须审查本次已提交改动；不要只看 HEAD 的差异。

按文件清单逐个读完 diff，并打开必要的上下文、调用方和测试；未跟踪文件不会出现在普通 diff 中，逐个打开本次新增文件。检查行为是否符合需求、接口是否真实可用、错误处理和敏感信息是否妥当。对删除、重命名、配置和依赖变更同样检查；生成文件或二进制无法逐行读时，核对来源和对应源码，明确未审查内容。用户原有或他人改动也要标明归属，不擅自删除。

发现问题时指出文件位置和影响，修复本次范围内能够确认的问题，不扩展成无关重构。若任务范围不完整，列出已查文件与未能确认的提交范围。

## 3. 排查临时内容

检查上述 diff 的新增行和全部新增文件，用 `rg -n` 辅助定位 `console.log`、`console.debug`、`debugger`、`print(`、`breakpoint(`，以及 mock、fake、临时返回值、固定用户 ID、写死 token、测试地址和测试数据。结合业务逐处判断：正式日志、测试用例和有用途的 fixture 可以保留；删除遗留调试输出和生产路径中的临时数据。未命中关键词不等于没有问题，仍需读完改动。

不要把疑似密钥的原值贴进日志或摘要；发现已提交凭证时只报告位置和类型，移除并提示轮换。不能把真实凭证替换成另一个硬编码值。

若第 2、3 步修改了代码或配置，重新运行第 1 步对应测试，再检查新增 diff 和临时内容，直到修改后的结果已核实，或有明确阻碍。结束前重新查看 git status 和改动清单，确认检查期间没有遗漏新文件。

## 4. 输出简短摘要

用一个简短段落说明实际改了什么、测试命令与结果、审查范围、已修复问题和仍未解决的阻碍。没有问题就写“未发现遗留调试代码或硬编码测试数据”，不要写无法证明的“绝对没有问题”。测试失败、检查范围不完整或外部验证未完成时明确保留该状态；全部完成且测试通过后才写“收工检查通过”。
